# Zwift Controller v0.8.1

Windows desktop bridge for Zwift Click V2 and MyWhoosh. Keyboard mode defaults to I/K for gear changes; U and social actions 1/2/3 were confirmed by the user; A/D and C remain to be validated. OpenBikeControl is experimental.

## Run

```powershell
py -3.12 -m pip install -r requirements.txt
py -3.12 -m unittest discover -s tests -v
py -3.12 desktop.py
```

The desktop uses two independent Bluetooth connections by default. Each controller has its own status and battery reading. Windows cached GATT reconnection is enabled by default, with an uncached discovery fallback. Preventive left-controller reboot is disabled by default. Save in the button editor or options dialog to persist settings and reconnect. Reset gauche requests a left-only manual reset. Closing the window minimizes to the tray; Quit disconnects. Keep MyWhoosh in the foreground and run both programs at the same Windows privilege level.

## Zwift authentication

If the left controller sends repeated FF 03 messages, the desktop recommends renewing authentication in the official Zwift application. Stop the bridge, pair both controllers in Zwift, close Zwift and restart the bridge. A short hardware test confirmed that both controllers continued working after official pairing; authorization lifetime remains to be measured. No automatic Zwift account authentication is implemented. The optional emergency reboot may interrupt input and is not a substitute for authentication.

## Console modes

```powershell
py -3.12 zwift_controller.py --dual --no-auto-reset --fast-reconnect
```

The command above uses keyboard output. Add --no-obc for Bluetooth only or --debug for raw diagnostics in debug.log. Use --discover to find controller addresses. The legacy single-connection CLI mode remains available without --dual; use --no-auto-reset to disable its idle reset. --refresh-handshake is experimental and did not prevent the observed authorization timeout. --fast-reconnect enables Windows GATT cache reuse; the actual speed improvement still needs hardware validation.

## Build executable

```powershell
powershell -ExecutionPolicy Bypass -File .\build.ps1
```

The script installs dependencies, runs unit tests and builds dist/ZwiftController.exe. The executable stores config.json in %LOCALAPPDATA%/ZwiftController; source mode uses the repository config.json. Move the executable to a permanent location before enabling Windows autostart. v0.7.1 GUI and executable require Windows validation.

## v0.7.1

New defaults: minus=I, plus=K, left=A, right=D, up=U, down=C, A=1, B=I, Y=2, Z=3. Legacy default values migrate automatically; custom values and disabled keys are retained. Apply saves the mapping version and per-button press modes (simple, held, repeat). The desktop displays button activity, recovery initialization time, authentication warnings per side, and foreground MyWhoosh status. Diagnostic logging is optional, with one rotated 5 MiB backup; export copies the active log. A Windows mutex prevents duplicate desktop instances (not separate CLI sessions). The bike icon is generated by bike_icon.py for the window, tray and build. Connection setup now runs outside the scan lock, and the final 300 ms handshake delay is removed. Actual Bluetooth performance and keyboard modes require hardware validation. No automatic updater is included.

## v0.7.2

Compact dashboard with two battery cards and live button indicators. Configure buttons in a separate editor with default/reset, cancel and save. Advanced settings live in Options; the Diagnostics window displays the last 500 log messages and provides export and left reset. Detailed raw logging remains optional. The Bluetooth algorithm and key defaults are unchanged. Windows layout and interaction require validation.

## v0.8.0

- The desktop and console entry points share the same named Windows mutex. Close an older bridge before starting the new version. A second instance cannot access the controllers.
- Independent connections report an advisory warning after 20 seconds without any notifications, or after repeated authentication challenges and 60 seconds without button frames. Idle button periods alone are not treated as failures. These warnings do not cause automatic resets.
- Failed cached GATT sessions fall back to uncached discovery; retry intervals are slightly shorter. Hardware timing remains to be validated.
- The tray tooltip displays the latest battery reading per connected controller; the desktop warns once per low-battery period below 15%.
- The desktop checks GitHub's latest stable release at startup and via Options. Only newer stable semantic versions are offered. The frozen Windows executable can install a release after user confirmation if the release includes a verified SHA-256 digest or a matching checksum asset. Source mode opens the release page instead. The helper waits for shutdown, atomically replaces the executable, keeps a .previous backup and restarts; failures are logged in .update.log. This is not code signing and relies on the integrity of the project's GitHub releases.
- To publish a stable release after validation, build the approved code, then attach dist/ZwiftController.exe and dist/ZwiftController.exe.sha256 to a non-prerelease GitHub Release tagged vX.Y.Z. No release is created automatically.
- Fitbit integration is not included. The Windows update flow, mutex and Bluetooth health thresholds require runtime validation.

## GitHub Actions builds

Every push to dev or main runs compilation, unit tests and a Python 3.12 Windows PyInstaller build. Download the ZIP artifact from the Windows build run under the Actions tab (14-day retention). It contains the executable and SHA-256 checksum.

Stable publication remains opt-in: after approving and merging the tested version into main, push the matching version tag (for example, v0.8.0 for VERSION = "0.8.0"). The workflow checks the tag and main ancestry, requires a successful Windows build and tests, verifies the checksum, and publishes a GitHub Release with both assets. Do not push a stable tag until hardware validation is complete. Development builds do not appear as automatic updates.

## v0.8.1

Small release for end-to-end update validation from 0.8.0. Checks for stable updates at startup and every six hours, notifies once when a newer release is found during the session, and prevents quitting while an update download is in progress. The installer starts the replacement from its own directory and records replacement and restart requests in the update log. The first update from 0.8.0 uses the existing 0.8.0 updater; new updater changes apply to subsequent updates. Bluetooth, keyboard mappings and Fitbit integration are unchanged.
